# 20260415 记忆已存但检索不到专项修复计划

## 背景

用户已经明确定位出 angel_memory 当前“记忆明明写进去了，但 recall 经常检索不到”的主矛盾不在写入链，而在 recall / query 处理链。结合现有代码核对后，可以确认问题主要集中在以下几层：

1. `tools/core_memory_recall.py` 过度依赖 LLM 显式传入 `time_range`，服务端没有做足够强的时间兜底。
2. `tools/core_memory_recall.py` 在 `comprehensive_recall()` 之后立即按 `is_active` 二次筛掉结果，可能把“命中了但被过滤”的情况误报成“完全没找到”。
3. `main.py` 中 `strict_time_recall = time_filter.matched and recall_request.matched` 门槛过高，导致明确时间语义不一定触发严格时间回捞。
4. `core/utils/query_processor.py` 对 `angelheart_context` 的类型兼容不一致，且 `process_query()` 存在确认成立的提前 `return`，会绕过 assistant name 过滤和后处理。
5. 链路日志虽然已有部分“时间过滤诊断”，但还不足以一眼判断问题究竟丢在 query 构建、时间识别、MemoryManager 召回还是 tool 层过滤。
6. 启动期 provider 状态日志存在时序误报，容易误导排错方向。

## 已确认的代码现状

### 1. `core_memory_recall` 现状

- 只有 `time_range` 显式传入且命中 `valid_time_ranges` 时，才会尝试 `sql_manager.recall_by_time(...)`。
- 否则直接退回 `memory_runtime.comprehensive_recall(query=...)`。
- `comprehensive_recall()` 返回后立刻执行：
  - `all_active_memories = [mem for mem in all_memories if mem.is_active]`
  - 如果 `all_active_memories` 为空，直接返回“没有找到相关的主动记忆”。
- 现有日志不足以区分：
  - 下层根本没命中
  - 下层命中了但都不是 active
  - 时间条件根本没有透传到召回层

### 2. `main.py` 现状

- `_inject_recent_raw_chat_anchor()` 中：
  - `time_intent = analyze_time_intent(message_text)`
  - `time_filter = build_time_filter_payload(time_intent)`
  - `recall_request = analyze_recall_request(message_text)`
  - `strict_time_recall = bool(time_filter.get("matched") and recall_request.get("matched"))`
- 这意味着即使用户说了“昨天 / 昨晚 / 前面 / 上周四”，只要 recall phrase 没命中，raw chat 严格时间回捞就不会启用。

### 3. `QueryProcessor` 现状

- `extract_rag_fields()` 和 `_extract_assistant_names()` 都直接 `json.loads(event.angelheart_context)`。
- `extract_rag_fields()` 捕获了 `TypeError`，但 `_extract_assistant_names()` 没有，异常处理不一致。
- `process_query()` 中如果 `rag_query` 非空且长度小于阈值，会直接提前返回，导致后续这些步骤被跳过：
  - `_extract_assistant_names()`
  - `_filter_assistant_names()`
  - `_clean_text()`
  - `_truncate_text()`

### 4. 时间识别现状

- `analyze_time_intent()` 已支持：
  - `昨天`
  - `昨晚`
  - `刚才`
  - `前面`
  - `上次`
- 但其中 `上次` 目前只有 `matched=True` 的语义说明，没有稳定的显式时间窗。
- `analyze_recall_request()` 仍然主要靠短语表触发，和时间识别没有形成“时间优先”的统一门控。

### 5. 下层检索能力现状

- `MemoryManager.comprehensive_recall()` 已支持 `time_filter`，并会在 SQL / hybrid / vector-only 分支里应用硬时间过滤。
- `MemoryManager` 本身已有基础时间过滤诊断日志。
- 因此本次优先修复不需要重写整个召回引擎，重点是：
  - 把时间窗稳定送到它
  - 避免 tool 层把它召回的结果误筛掉
  - 把日志补完整

## 本次实现范围

本轮只处理 recall / query 链的高优先级问题，按用户指定优先级执行：

1. `core_memory_recall` 的服务端时间兜底
2. `core_memory_recall` 的 active 假阴性修复
3. `main.py` 的 `strict_time_recall` 放宽
4. `QueryProcessor` 的 `angelheart_context` 类型兼容
5. `QueryProcessor.process_query()` 取消提前 return，统一后处理流水线
6. recall / query / retrieval 链路日志补齐
7. 时间识别与 recall request 的服务端兜底增强
8. provider 启动日志去误导化

## 实施方案

### 第一阶段：修复 `core_memory_recall` 的时间兜底与假阴性

涉及文件：

- `tools/core_memory_recall.py`
- 可能补充到 `core/utils/time_diagnostics.py`

计划改动：

1. 扩展工具参数，增加：
   - `original_user_text`
   - `original_query`
2. 在 tool 内统一解析时间来源，优先级为：
   - 显式 `time_range`
   - `original_user_text`
   - `original_query`
   - `query`
3. 只要识别出明确时间窗，就优先构造 `time_filter` 并走硬时间过滤：
   - 优先使用 `recall_by_time()`（当运行时可安全拿到 SQL manager 且 time_range 可映射）
   - 否则退化为 `memory_runtime.comprehensive_recall(..., time_filter=...)`
4. 对命中结果增加完整统计日志：
   - `total_hits`
   - `active_hits`
   - `inactive_hits`
   - `filtered_reasons`
5. 当 `total_hits > 0 and active_hits == 0` 时，不再直接返回“没有找到相关的主动记忆”：
   - 优先降级返回总命中的最相关若干条
   - 同时在日志明确标记“命中了但都被 active 过滤”
6. 检查 `is_active` 缺省值与读取逻辑，避免因为历史数据或默认值导致工具层大面积假阴性。

### 第二阶段：放宽 `main.py` 的严格时间回捞门槛

涉及文件：

- `main.py`
- 可能补充到 `core/utils/time_diagnostics.py`

计划改动：

1. 重构 `_inject_recent_raw_chat_anchor()` 中的回捞判定逻辑。
2. 将 `strict_time_recall` 从：
   - `time_filter.matched and recall_request.matched`
   改为：
   - 只要 `time_filter.matched` 且存在明确时间窗，就允许 strict time recall
3. `recall_request.matched` 改为增强信号，不再作为硬门槛。
4. 对明确时间表达优先走 raw chat 时间窗口检索，尤其覆盖：
   - `昨天`
   - `昨晚`
   - `刚才`
   - `前面`
   - `上次`
   - `之前`
   - `那会儿`
   - `上周四`
5. 统一把判定结果记入 diagnostics，明确区分：
   - 时间命中了但 recall phrase 没命中
   - recall phrase 命中了但没有显式时间窗
   - 两者都命中

### 第三阶段：修复 `QueryProcessor` 的类型兼容和后处理绕过

涉及文件：

- `core/utils/query_processor.py`

计划改动：

1. 新增统一 helper，例如 `_load_angelheart_context(event)`：
   - `dict` 直接返回
   - `str` 尝试 `json.loads`
   - 其他类型返回 `{}`
2. 让以下函数统一走该 helper：
   - `extract_rag_fields()`
   - `_extract_assistant_names()`
3. 统一异常处理与日志，不再出现一个函数吞 `TypeError`、另一个函数漏掉的情况。
4. 改写 `process_query()` 控制流，改成统一流水线：
   1. 先决定用 `rag_query` 还是 `original_query`
   2. 再统一执行 assistant name 过滤
   3. 再执行 clean / truncate
   4. 最后返回
5. `preprocess_skipped` 只表示“某些预处理未执行”，不再允许它绕过整个后处理链。

### 第四阶段：补齐链路日志与服务端兜底识别

涉及文件：

- `tools/core_memory_recall.py`
- `core/utils/query_processor.py`
- `main.py`
- `llm_memory/service/memory_manager.py`
- 如有必要，补充 `core/services/retrieval_service.py`

计划改动：

1. 每次 recall 记录完整链路日志，至少包括：
   - `raw_user_input`
   - `original_query`
   - `tool query`
   - `tool time_range`
   - `analyze_time_intent(raw_user_input)`
   - `analyze_time_intent(original_query)`
   - `analyze_time_intent(tool query)`
   - `analyze_recall_request(raw_user_input)`
   - query 构建阶段 `secretary_topic / entities / facts / keywords`
   - `QueryProcessor` 的 `rag_fields / rag_query / final_query`
   - `comprehensive_recall` 总命中数
   - `active` 过滤前后数量
   - 最终返回给 LLM 的记忆数量
2. 区分三类日志结论：
   - 上游 secretary 字段本来就是空
   - 本地解析失败
   - MemoryManager 已命中但 tool 层二次筛掉
3. 在时间识别规则上补充更稳的服务端兜底：
   - 优先级上让明确时间语义高于 recall phrase
   - 对 `上次 / 前面 / 之前 / 那会儿 / 上周四` 增加归一化支持

### 第五阶段：顺手修正 provider 启动日志

涉及文件：

- `main.py`
- 如有必要，相关 provider / initialization 状态获取文件

计划改动：

1. 区分三种状态：
   - 已配置但注册表未就绪
   - 已配置且可用
   - 未配置
2. 避免在启动早期过早输出“将使用本地模式”这类最终结论式日志。

## 验收标准

### 行为验收

1. 用户问“昨天我们聊了什么”“昨晚你还记得吗”“上周四那个事你还记得吗”时，即使 LLM 没传 `time_range`，也能稳定按时间窗检索。
2. 如果 MemoryManager 已命中结果，`core_memory_recall` 不再无声吞掉：
   - 要么返回结果
   - 要么明确说明被哪一层过滤
3. `QueryProcessor` 必须兼容 `angelheart_context` 的 `dict / str` 两种形态。
4. `process_query()` 不再通过提前 `return` 绕过 assistant name 过滤和其他后处理。
5. 日志里必须能完整看到：
   - `raw_user_input`
   - `original_query`
   - `tool query`
   - `time_range`
   - `secretary_*` 原始值
   - `rag_fields / rag_query`
   - `total_hits / active_hits / final_returned_hits`
6. 本次复现样例不能再出现：
   - `MemoryManager 命中 3 条 2026-04-09 相关长期记忆，但 core_memory_recall 返回没有找到相关的主动记忆`

### 工程验收

1. 本次行为变更完成后，同步更新 `metadata.yaml` 的 `version`。
2. 优先补本地可运行的最小验证：
   - 时间识别单测或等价校验
   - `QueryProcessor` 类型兼容与统一后处理校验
   - `core_memory_recall` active 降级返回校验
3. 实现完成后先等待用户生产环境验证通过，再归档计划到 `plan/done/`。

## 风险与注意事项

1. `上次 / 前面 / 之前 / 那会儿` 并不总能映射成唯一确定的时间窗，本轮应优先保证“有明确时间窗时一定硬过滤”，对模糊时间表达采取保守兜底，避免误过滤。
2. 工具层对 `is_active` 的降级策略需要兼顾原设计语义，避免把“主动记忆工具”完全退化成“任意记忆检索工具”。
3. 链路日志需要足够详细，但要避免在高频循环里打印过多逐条 INFO 明细，遵循仓库既有日志规范，聚合信息放 INFO，明细放 DEBUG。

## 执行顺序

按用户要求执行：

1. `core_memory_recall` 服务端时间兜底
2. `core_memory_recall` active 假阴性修复
3. `main.py` strict time recall 放宽
4. `QueryProcessor.process_query()` 统一后处理
5. `QueryProcessor` `angelheart_context` 类型兼容
6. recall / query / retrieval 链路日志补齐
7. 时间识别与 recall request 规则增强
8. provider 启动日志修正
