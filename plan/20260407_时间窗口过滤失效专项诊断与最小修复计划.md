# 20260407 时间窗口过滤失效专项诊断与最小修复计划

## 背景

用户反馈已经加过“按时间窗口过滤”的逻辑，甚至手动设置过时间范围，但在真实对话中：

- 问“昨晚我们聊了什么”仍会召回前天或更早的旧内容
- 问“我刚才说了什么”仍可能走长期语义记忆，或直接回答没有记录
- 体感上看不到时间过滤真正成为总闸门

本次任务分两阶段执行：

1. 先做真实调用链诊断与可观测性增强
2. 在根因确认后做最小修复

## 当前已确认的链路事实

### 1. 自动检索主链没有接入时间窗口参数

主链为：

`main.py -> PluginManager -> DeepMind.organize_and_inject_memories() -> DeepMindRetrievalService.retrieve_memories_and_notes() -> memory_runtime.chained_recall() / note_service.search_notes_by_top_k()`

已确认：

- `DeepMindRetrievalService` 调用 `memory_system.chained_recall(...)` 时没有 `time_range/start_time/end_time`
- `MemoryRuntime` 协议没有时间窗口参数
- `VectorMemoryRuntime` / `SimpleMemoryRuntime` 都没有时间窗口透传
- `CognitiveService` / `MemoryManager` 的 `comprehensive_recall`、`chained_recall` 也没有时间窗口参数
- `NoteService.search_notes_by_top_k()` 没有时间窗口参数

结论：自动长期记忆检索和笔记检索当前都不受时间窗口控制。

### 2. 现有“时间过滤”只存在于工具分支

仓库内仅发现以下真实时间过滤实现：

- `tools/core_memory_recall.py`
- `llm_memory/components/memory_sql_manager.py::recall_by_time`

其中 `recall_by_time` 是真正的 SQL 硬过滤：

- 先解析 `time_range -> start_ts/end_ts`
- 再执行 `WHERE created_at >= ? AND created_at <= ?`

但这条逻辑仅存在于 `core_memory_recall` 工具路径，不在自动召回主链中。

### 3. 工具分支的时间过滤本身存在接线问题

`core_memory_recall.py` 当前通过：

`sql_manager = getattr(memory_runtime, "sql_manager", None)`

来查找 `recall_by_time`。

但当前运行时实现为：

- `SimpleMemoryRuntime` 持有的是 `self._manager`
- `VectorMemoryRuntime` 持有的是 `self._cognitive_service`

两者都没有暴露 `sql_manager` 属性。

结论：看起来“写了时间过滤”，但运行时大概率根本拿不到 `sql_manager`，属于半接线状态。

### 4. 时间语义会在 query 构造阶段被冲淡甚至丢失

`DeepMind.organize_and_inject_memories()` 中：

- 若存在 `secretary_decision`，会用 `topic + entities + facts[:3] + keywords[:3]` 重建 `query`
- 不会保留用户原始问题文本

随后 `QueryProcessor.process_query()` 中：

- 会再次优先使用 `extract_rag_fields()` 提取的 `entities/facts/keywords`
- `_build_rag_query()` 完全不包含 `topic`
- 也没有任何时间意图字段或时间范围字段

结论：

- 原始问题中的“昨晚/昨天/刚才/前面”可能在 `secretary_decision` 分支就已经丢失
- 即便 `DeepMind` 构造的中间 query 含有 `topic`，`QueryProcessor` 仍可能把它替换成仅含 `entities/facts/keywords` 的 query

### 5. 原始聊天窗口是独立系统，不参与统一时间过滤

`main.py` 当前只做了：

- 每次请求从 `raw_chat_window.db` 取最近 15 条
- 注入到 `request.system_prompt`

但它没有：

- 解析“昨晚/刚才”等时间意图
- 按具体时间范围查 raw chat
- 参与 `retrieval_service` 的统一召回排序

结论：原始聊天窗口目前只是 prompt 锚点，不是统一的时间窗口检索分支。

### 6. 后续融合与最终注入仍可能把旧内容重新混回来

已确认：

- rerank / hybrid retrieval 只看语义，不看时间
- `session_memory_manager` 会把本轮召回到的长期记忆累计进会话短时池
- 最终注入给模型的是整个 session memory，而不是“仅本轮时间窗口命中”

结论：即便前面某一步有时间倾向，后面也可能被旧记忆再次冲淡。

## 第一阶段实施内容

仅做诊断与可观测性增强，不先大改结构：

1. 给 `DeepMind` 增加时间意图诊断日志
2. 给 `QueryProcessor` 增加原始 query / 中间 query / 最终 query 日志
3. 给 `RetrievalService` 增加检索参数、候选数量、来源与时间分布日志
4. 给长期记忆检索和笔记检索补充“是否收到时间参数”的日志
5. 给 rerank 前后结果增加 topN 时间分布日志
6. 给最终注入阶段增加“最终注入了哪些记忆/来源/时间”的日志
7. 给“没有记忆”路径补明确原因日志

## 第二阶段最小修复原则

确认根因后，只做最小修复，优先级如下：

1. 让“昨晚/昨天/刚才/前面”等时间语义成为统一的硬约束，而不是弱排序信号
2. 优先保证自动检索主链能真正收到并执行时间窗口
3. 原始聊天窗口存在时，优先作为“刚才/前面”类问题的兜底
4. 避免只有工具分支支持时间过滤，其他主链继续绕过
5. 避免修复后被 session memory / rerank / notes 注入再次冲淡

## 计划中的最小修复方向

以最小改动为目标，倾向于：

1. 新增统一时间意图解析结果对象
2. 在 `DeepMind -> RetrievalService -> MemoryRuntime -> MemoryManager` 这条主链透传时间窗口
3. 将长期记忆检索改成“先时间硬过滤，再做现有语义召回/融合”
4. 对“我刚才说了什么/前面提过吗”类问题，优先走 raw chat 时间窗口检索或直接命中 raw chat 锚点
5. 修正 `core_memory_recall` 通过 `memory_runtime` 取不到 `sql_manager` 的接线问题
6. 让最终注入日志明确区分：
   - 原始聊天窗口
   - 长期记忆
   - 笔记
   - 历史 session 池残留

## 验证用例

### case 1

输入：`昨晚我们聊了什么？`

期望：

- 明确识别 `last_night`
- 日志打印出起止时间
- 最终结果来源以昨晚范围内记录为主

### case 2

输入：`我刚才说了什么？`

期望：

- 优先命中 raw chat 或最近事实层
- 不应优先跑去长期旧记忆做语义联想

### case 3

输入：`昨天是不是聊过健身？`

期望：

- 最终结果以昨天范围内“健身”相关记录为主
- 更早“健身”记忆不能因为语义相似而压到前面

### case 4

输入：普通无时间意图问题

期望：

- 不误触发时间过滤
- 维持原有正常召回路径
